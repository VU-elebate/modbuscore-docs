ModbusCore++ — Design Overview

Purpose

ModbusCore++ is a transport-agnostic Modbus library written in C++20. It targets FreeRTOS-based embedded hardware but can also run on Linux and Windows via a thin set of desktop stubs. The library implements the Modbus application layer; hardware-specific I/O is handled entirely by user-provided Communication subclasses.

▲

└── ModbusCore::Client (master: sends requests, receives responses)

CRTP pattern

Device<T> uses the Curiously Recurring Template Pattern so that Server and Client share all memory-block logic and communication wrappers without virtual dispatch.

class Server : public Device<Server> { ... };
class Client : public Device<Client> { ... };

Template instantiations are explicit and live in src/device.cpp. Adding a new Device specialisation requires updating that file.

Because Device<Server> and Device<Client> are distinct template instantiations they each have their own set of static mutexes — the two memory domains are independent.

Memory model

Each Device<T> instance holds four Modbus memory blocks, protected by per-type static mutexes:

Block Access Cell size Mutex
Discrete Inputs Read-only 1 bit discreteInputMutex
Coils Read-write 1 bit coilsMutex
Input Registers Read-only 16 bit inputRegistersMutex
Holding Registers Read-write 16 bit holdingRegistersMutex

Bit-addressed blocks pack 8 values per MemoryCell byte. The size of each vector is determined by the constructor arguments (numDiscreteInput, numCoils, etc.).

Communication abstraction

ModbusCore::Communication is an abstract base class that decouples the Modbus application layer from any specific transport:

class Communication {
public:
virtual ModbusErrorCode readData(PDU &frame) = 0;
virtual ModbusErrorCode writeData(PDU &frame, AddressType addr) = 0;
};

Implementors are responsible for:

  • Serial (RTU): framing with ADU (slave address + PDU + CRC). Helper methods createSerialPacket and checkCRCSerialPacket are provided in the base class.
  • TCP/IP (MBAP): framing with MBAP header (transaction ID, protocol ID, length, unit identifier). Helper methods createTCPIPPacket and serializeMBAP/MBAPFromSerializedData are provided.

The base class also manages:

  • addressesFIFO — FIFO of incoming sender addresses (populated by readData, consumed by respond).
  • addressHashTable — maps IP addresses to pending (transaction ID, unit identifier) pairs for TCP/IP request-response matching.

Data structures

PDU

[ function code (1 byte) | data (variable) ]

The core Modbus Protocol Data Unit. All function code logic operates on PDU.

ADU (Serial RTU)

[ slave address (1 byte) | PDU | CRC (2 bytes) ]

MBAP (TCP/IP)

[ transaction ID (2) | protocol ID (2) | length (2) | unit identifier (1) | PDU ]

length = 1 (unit identifier) + 1 (function code) + data size.

Server: advances one state per call — call from an application loop or RTOS task.
Client: spins internally through all states in a single processRequest() call, blocking in WaitForRequest until the transport delivers a frame.

Adding a new function code

  1. Add the code to ModbusFunctionCode enum in include/utils.h.
  2. Handle it in Server::PDUChecking and Server::ServiceProcessing in src/core/server.cpp.
  3. Handle it in Client::PDUChecking and Client::ServiceProcessing in src/core/client.cpp (for the response the client receives back).
  4. If the function code requires new Device memory operations, add them to Device<T> in include/device.h and src/device.cpp, and add an explicit instantiation for both Server and Client.
  5. Add a test case to tests/core/RequestTest.cpp.

Desktop stubs (FreeRTOS)

The library depends on FreeRTOS primitives (SemaphoreHandle_t, xSemaphoreCreateMutex, etc.). When building for desktop the stubs in tests/stubs/ provide thin wrappers over std::mutex:

FreeRTOS primitive Desktop stub
SemaphoreHandle_t std::mutex*
xSemaphoreCreateMutex() new std::mutex()
xSemaphoreTake(h, _) h->lock()
xSemaphoreGive(h) h->unlock()

These stubs are only compiled in when MODBUS_TESTS=ON (the default).
